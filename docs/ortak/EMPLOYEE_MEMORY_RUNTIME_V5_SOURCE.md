# Employee reviewed runtime source cutoff

This source implements the explicit ordinary runtime branch after the held
employee storage, source-authority and protocol fragments. No numbered migration,
current deployment, runtime selection, provider run, PostgreSQL result or UI
recall acceptance is claimed by this document. Root runs all gates.

## Explicit selection and actual request

Each existing owned worker employee entry may add
`reviewed_employee_destinations: [{target_id, destination_channel_id}]`. Absence
keeps the existing snapshot1–4 path. There are at most16 distinct destinations
per employee and128 per worker recipe; every entry requires its full original
creation receipt. The target must already have the privately validated namespace
registration and independent fixed expiry. The worker only converges its
`runtime_consumption_enabled` flag; removing/re-enabling selection advances the
consumption epoch. It does not extend expiry or run a new diagnostic.

The SQL origin resolver reconstructs a decided human Office routing decision,
recipient and delivery reservation, or the exact original author of a promoted
Work source under current Work/project authority. Manual Work and confidential
payloads are excluded before the new remote read. Own human plaintext source,
current human and employee membership in both source and destination, exact
source partition/evidence and retained channel authority rows are required.
Missing source authority registration is refusal, never implicit registration.
The source and destination can differ. The namespace never has a project wrapper.

Candidate filtering applies current source, destination, original sharing,
target, publication ACK and actual-requester checks before LIMIT32. Relationship
facts must name that exact requesting human. Experience remains limited to its
explicit destination. The selector locks scopes, sorted facts and the target,
re-reads exact IDs, then requests at most8 pins in relationship/experience/UUID
order. Local content is used only for validation and byte budgeting, discarded
before the adapter request, and never used to replace remote content.

The adapter re-inspects the same original owned namespace and compares its
company, employee, deployment, original receipt and distinct binding/namespace
hashes. It performs selected recall only. Missing remote records stay missing.
After HTTP the selector rechecks current origin and exact returned pins. Freeze,
held start, output materialization and Office publication use the same current
predicate with retained epochs and sorted locks. Stop rejects old uses immediately
without waiting for remote withdrawal; accounting-only lost-ACK cleanup remains
available through the existing narrowly bounded exception.

## Immutable snapshot5

The optional top-level `employee` field is absent in snapshot1–4. Version5 has
neither top-level `reviewed` nor `conversation`. Its employee context is:

```text
{origin: canonical JSON string,
 conversation_origin?: unchanged version4 origin,
 records: [{scope: employee|conversation|project, record: exact typed record}],
 truncated: boolean}
```

At least one actual remote employee record is required. An empty employee result
returns the existing1–4 result. Employee records precede existing reviewed
records; scratch renders last. The remaining adapter wrapper limits old-family
remote requests to the record slots left by the actual employee response.
The retained context has at most8 reviewed records/8192 content bytes, and at
most8 total records/16384 content bytes including scratch. Every rendered string
is at most8192 bytes. Project and conversation record/rendering bytes are unchanged.
The existing SQL72 reversible NUL comparison and original scratch-byte accounting
are preserved. No source text is copied into approved content.

The employee pin has exactly15 fields: `fact_id`, `target_id`, `fact_version`,
`content_hash`, `source_hash`, `sharing_hash`, `audience_hash`, `binding_hash`,
`namespace_hash`, `approval_id`, `approved_by`, `expires_at`,
`source_authority_epoch`, `destination_authority_epoch`, `consumption_epoch`.
Provenance is the unchanged canonical employee v1 string, including its distinct
sharing approval. The rendered wrapper has `type: reviewed_employee_memory`,
`trust: untrusted_data`, and the exact record.

The separate origin format is `ortak-reviewed-employee-run-origin/1`, with
lexicographically ordered compact JSON keys: `company_id`,
`destination_authority_epoch`, `destination_channel_id`, `employee_id`, `format`,
`requester_public_key`, `source`, `source_authority_epoch`. Source keys are
`author_public_key`, `channel_id`, `community_id`, `event_created_at`, `event_id`,
`evidence_hash`. Timestamps have exactly6 fractional digits and UTC `Z`. It carries
no sharing approval and is a historical claim, not concurrency authority.

## Persistence, scheduling and assembly

reviewed ordinal0–7, exact15 pin fields and company/community/run identity.
Existing `run_reviewed_memory_uses` columns retain their meanings. Deferred
validation binds the complete mixed set, render order, exact original bytes,
origin, scope and current permissions; updates/deletes/truncation are refused.
Both namespaces must be included in later canonical deletion/G inventory review.

existing export scheduler. Only the exact configured original receipt can write.

does not create approval or grant runtime use. Cleanup uses original ownership

Required disposable PostgreSQL/HTTP gate uses the existing signed employee

expiry renewal; forged record/provenance/origin/order/NUL/render/snapshot/use rows
are refused. No direct fabricated snapshot/use/ACK shortcut proves these cases.
These integration fixtures and actual results remain a gate, not an assertion.
